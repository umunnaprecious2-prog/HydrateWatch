## Last Completed Work

- Removed the legacy Python/FastAPI/SQLAlchemy backend (`backend/app`,
  `alembic/`, `requirements.txt`, venvs) - it's fully superseded now.
- Backend is TypeScript + Express + Prisma, running against **CockroachDB**.
  Prisma's `datasource` uses `provider = "cockroachdb"` - this is
  required, not a style choice: confirmed directly against a live
  cluster that Prisma's schema engine hard-refuses `migrate deploy` /
  `db push` with `provider = "postgresql"` even though CockroachDB is
  otherwise Postgres-wire-compatible. IDs use `@default(sequence())`
  (CockroachDB only allows `autoincrement()` on `BigInt`); migration SQL
  uses CockroachDB's dialect (`STRING`/`INT4`/`GENERATED BY DEFAULT AS
  IDENTITY`), generated offline via `prisma migrate diff --from-empty`.
- **Fully verified against the user's real CockroachDB cluster**
  (`hydratewatch-db`, AWS us-west-2): migration applied cleanly, all 6
  tables + `_prisma_migrations` exist, `npm run dev` connected and
  served `/api/v1/health` as 200, a real `/api/v1/auth/register` call
  round-tripped a user into the database (then cleaned up), and the
  Docker image (the exact one Render will run) did the same via
  `docker compose up backend`. Two real issues found and fixed along
  the way:
  - `sslmode=verify-full` needs a local root CA bundle file most
    machines don't have configured for Postgres tooling - switched to
    `sslmode=require` (still encrypted, skips CA-chain verification).
  - CockroachDB Cloud auto-locks a table's schema right after creation
    (changefeed optimization); a migration that creates a table then
    later indexes/references it in the same migration needs explicit
    `ALTER TABLE ... SET (schema_locked = false);` right after each
    `CREATE TABLE`, which the current migration file has.
  - Also added `connect_timeout=30&pool_timeout=30` to the connection
    string - Prisma's default 10s pool timeout was intermittently too
    tight for this network path (saw both fast successes and P1001
    timeouts on identical connection attempts).
- Wired up ESLint + Prettier for the backend (`npm run lint` / `format`)
  and fixed the lint errors that surfaced.
- Dockerized backend + frontend: `backend/Dockerfile`,
  `frontend/Dockerfile`, root `docker-compose.yml` (backend + frontend
  only now - no bundled local db service; point `DATABASE_URL` at a
  real CockroachDB cluster, Cloud Serverless free tier works for local
  dev too). Fixed three Docker bugs along the way: Prisma's telemetry
  hanging with no outbound network, Prisma's engine needing OpenSSL on
  `node:20-alpine`, and Next's standalone server binding to Docker's
  auto-set `HOSTNAME` instead of all interfaces.
- Added `render.yaml` (Render Blueprint) and **deployed both services live**
  via the user clicking through the Render dashboard. Verified for real,
  not just theoretically: CORS reflects the frontend's origin correctly,
  the frontend's JS bundle has the right backend URL baked in (inspected
  the actual deployed chunk), and a real registration request sent exactly
  as the live frontend would send it round-tripped a user into production
  CockroachDB.
- Fixed a `tailwindcss`/`postcss`/`autoprefixer` bug that broke the
  frontend's first Render build: they were `devDependencies`, and Render
  sets `NODE_ENV=production` before `npm install`, which skips
  `devDependencies` entirely - but `next build` still needs them. Moved
  to `dependencies`.
- Fixed a floating-point display bug (`32.400000000000069%` instead of
  `32.4%`) in the dashboard's System Health widget and risk-alert
  messages - `100 - hydrate_risk` wasn't rounded.
- **Converted the frontend to a static export** (`next.config.js`:
  `output: "export"`, `trailingSlash: true`) and switched
  `hydratewatch-frontend` on Render from a Node Web Service to a Static
  Site (`runtime: static`, `staticPublishPath: ./out`) - eliminates the
  free-tier cold-start delay entirely (Static Sites are CDN-served,
  always-on; Web Services sleep after 15 min idle and take ~30-60s to
  wake). Confirmed every route was already prerendering as static (no
  route handlers, middleware, dynamic segments, or `next/image` usage)
  before making the switch, so nothing changed behaviorally. Updated
  `frontend/Dockerfile` to serve the exported `out/` directory via nginx
  instead of `next start` (kept for local `docker compose` parity only -
  production hosting is Render's static site infra, not this Dockerfile).
  Verified locally: raw static server, then the full nginx Docker image,
  both serving all routes and a real 404 correctly.
- Added `FRONTEND_URL` env var (backend CORS) and tightened CORS to
  reject unknown origins in production (it previously allowed any
  origin unconditionally, even with `credentials: true`).
- Restored `claude.md` to the full HydrateWatch operating rules (a
  stray generic template had overwritten it); removed the leftover
  `claudee.md`, `prep.md`, `instruction.md` scaffolding.
- Shipped a small frontend fix: sensor data now refetches immediately
  after a successful upload instead of waiting for the next poll.
- Updated the CV (`CV_updated.pdf`) with a HydrateWatch project entry
  matching the Gpron/Play entries' style, replacing a stale entry about
  an older Streamlit prototype.
